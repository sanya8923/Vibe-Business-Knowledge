# VPS-инфраструктура для AI-агента, автоматизаций, лёгкого backend и ComfyUI

**Дата актуализации:** 24 августа 2026 года
**Статус:** сводное исследование; цены, наличие промотарифов и правила регистрации необходимо повторно проверять перед оплатой
**Конфиденциальность:** документ не содержит имён, контактов, адресов, IP-адресов, SSH-ключей, платёжных реквизитов, названий закрытых репозиториев и сведений о конкретных частных проектах

---

## 1. Назначение исследования

Документ суммирует практические выводы по выбору и построению недорогой серверной инфраструктуры для четырёх типовых нагрузок:

1. автономный AI-агент с доступом к терминалу, файлам и браузеру;
2. лёгкий публичный backend с PostgreSQL, ботом или API и несколькими небольшими сайтами;
3. n8n или аналогичный оркестратор автоматизаций;
4. разработка расширений и workflow для ComfyUI с выполнением генераций на отдельной GPU-машине.

Исследование объединяет:

- официальную документацию провайдеров;
- фактические экраны заказа;
- реальный обезличенный процесс регистрации и общения с поддержкой;
- отзывы пользователей;
- архитектурный анализ безопасности AI-агента;
- оценку полной стоимости с учётом оплаты, продления, backup и GPU.

Исходное теоретическое сравнение VPS-провайдеров правильно выделяло главную ценовую ловушку: сравнивать нужно не приветственную цену первого срока, а стоимость продления. Оно также обращало внимание на промотарифы Tencent и Contabo, ограничения Oracle Free Tier и возможное отсутствие реальной экономии у российских хостингов. Расширенное исследование добавляет безопасность агента, shared CPU, GPU-архитектуру, независимые backup и практические сложности регистрации.

Это не независимый долговременный benchmark физических серверов. Производительность бюджетного VPS может зависеть от конкретного узла, соседей, региона и степени переподписки ресурсов.

## 2. Основные выводы

### 2.1. Для ранней разработки допустим один VPS

Один сервер на **4 vCPU и 8 ГБ RAM** способен одновременно обслуживать:

- AI-агента;
- Chromium или Playwright;
- n8n;
- тестирование Python- и Node.js-кода;
- исходники расширений ComfyUI;
- workflow и диспетчер GPU-заданий;
- несколько небольших development-сервисов.

Такой вариант проще в обслуживании: один IP, один firewall, один backup-план и одна операционная система.

Недостаток — единая точка отказа. Ошибка агента, переполнение диска, OOM, компрометация хоста или неудачное обновление могут затронуть все сервисы.

### 2.2. Два небольших VPS часто выгоднее одного большого

Рациональное разделение:

- **development/untrusted zone:** AI-агент, браузер, n8n development, код расширений ComfyUI, тесты и staging;
- **stable/public zone:** reverse proxy, публичный backend, PostgreSQL, бот/API и небольшие сайты.

Второй сервер нужен не столько ради дополнительной RAM, сколько ради уменьшения blast radius. Экспериментальный контур можно переустанавливать и ломать, не останавливая публичные сервисы.

### 2.3. Для production агент и backend следует разнести

Контейнер полезен как внутренняя «коробка», но не является полной границей безопасности: контейнеры используют общее ядро Linux и зависят от одного хоста.

Официальная модель безопасности Hermes Agent подчёркивает, что approvals, redaction, scanners и allowlists являются дополнительными эвристиками. Надёжная граница против ошибочного или враждебного поведения модели создаётся изоляцией на уровне операционной системы. Для работы с открытым вебом, почтой, недоверенным вводом и production рекомендуется изолировать весь процесс агента.

### 2.4. ComfyUI должен исполняться на GPU-машине

CPU-VPS может хранить:

- custom nodes;
- workflow JSON;
- manifests моделей;
- исходный код;
- тесты, не требующие CUDA;
- API и очередь заданий;
- deployment scripts.

Но стандартный ComfyUI не «подключает» удалённую GPU как прозрачное устройство. Workflow отправляется на `/prompt`, проходит валидацию, попадает в очередь и исполняется `PromptExecutor` на машине, где запущен runtime и доступны GPU и VRAM. Следовательно, полноценный ComfyUI с моделями должен работать локально или на облачном GPU-worker. Это архитектурный вывод из официальной модели исполнения ComfyUI.

## 3. Оценка ресурсов

### 3.1. AI-агент

Официальная документация Hermes Agent указывает:

- минимум: 1 CPU и 1 ГБ RAM;
- рекомендуемый уровень: 2 CPU и 2–4 ГБ RAM;
- активная браузерная автоматизация — наиболее требовательный режим, для неё рекомендуется не менее 2 ГБ.

Практический диапазон:

| Компонент | Обычный расход RAM |
|---|---:|
| Linux и системные службы | 0,3–0,7 ГБ |
| Docker, reverse proxy, VPN | 0,15–0,4 ГБ |
| AI-агент без браузера | 1–2 ГБ |
| Один Chromium-сеанс | дополнительно 0,5–1,5 ГБ |
| n8n | 0,3–1 ГБ |
| PostgreSQL небольшой системы | 0,15–0,5 ГБ |
| Лёгкий API или bot worker | 0,1–0,4 ГБ |

Практические уровни:

- **2 ГБ:** один лёгкий сервис либо очень аккуратный агент без постоянного браузера;
- **4 ГБ:** рабочий минимум для агента с браузером или небольшого backend с БД;
- **8 ГБ:** комфортный development-host для агента, n8n, браузера, тестов и нескольких небольших сервисов.

Swap на 1–2 ГБ полезен для переживания краткого пика. Постоянно заполненный swap означает недостаток RAM или необходимость разделения сервисов.

### 3.2. Публичный backend

Для небольшого числа пользователей 2 ГБ RAM обычно достаточно, если сервер содержит:

- Caddy или Nginx;
- один лёгкий backend-процесс;
- один worker;
- PostgreSQL с небольшой БД;
- несколько статических сайтов;
- базовый мониторинг.

Два гигабайта быстро заканчиваются при нескольких SSR-приложениях Node.js, тяжёлых фоновых workers, больших кешах, одновременных сборках или постоянной обработке файлов.

Для небольших сайтов предпочтительна схема:

```text
React/Vite build
        ↓
статические файлы
        ↓
Caddy/Nginx
```

Она заметно экономнее, чем несколько постоянно работающих development- или SSR-процессов.

### 3.3. Диск

| Объём | Практическое назначение |
|---:|---|
| 40 ГБ | один лёгкий backend или utility node |
| 60 ГБ | агент, n8n, несколько репозиториев и контейнеров |
| 80–100 ГБ | несколько окружений, Docker images и build cache |
| 128–256 ГБ | большие артефакты, локальные mirrors и много контейнеров |

Модели ComfyUI, text encoder, VAE и набор LoRA способны занять десятки гигабайт. Их не следует постоянно хранить на малом CPU-VPS. Они должны находиться на локальной GPU-машине, persistent volume облачного GPU-worker или в объектном хранилище.

## 4. Архитектурные варианты

### 4.1. Один VPS для development

```text
Internet
   │
   ├── 443 → reverse proxy → dev API / n8n webhook
   │
   └── Tailscale → SSH / admin UI

VPS 4 vCPU / 8 GB
├── agent-stack
│   └── AI-агент + браузер
├── automation-stack
│   └── n8n + собственная БД
├── comfy-dev
│   ├── custom nodes
│   ├── workflow JSON
│   ├── tests without GPU
│   └── job dispatcher
└── monitoring / backup scripts
```

Преимущества:

- минимальная операционная сложность;
- достаточно RAM для активной разработки;
- одна панель и одна точка администрирования;
- удобно для временных сервисов.

Недостатки:

- единая точка отказа;
- AI-агент находится рядом с n8n credentials и исходниками;
- один OOM или сбой диска останавливает всё;
- контейнеры не дают полной изоляции от захвата хоста.

Такой вариант подходит для development и staging при условии внешнего backup и отсутствия production-секретов.

### 4.2. Два бюджетных VPS

```text
VPS A — DEVELOPMENT / UNTRUSTED
4 vCPU / 8 GB
├── AI-агент
├── Chromium
├── n8n development
├── ComfyUI custom nodes
├── workflows / dispatcher
└── staging

          Git / private API / Tailscale
                       │
                       ▼
VPS B — STABLE / PUBLIC
2 vCPU / 2 GB
├── Caddy
├── bot / API backend
├── PostgreSQL
├── 1–3 light websites
└── external monitoring
```

Преимущества:

- агент физически отделён от публичной БД;
- две независимые точки отказа;
- development-сервер можно переустанавливать отдельно;
- меньше последствий prompt injection или ошибочной команды;
- один VPS может контролировать доступность другого.

Недостатки:

- две ОС и два firewall;
- требуется формализовать deploy и сетевые разрешения;
- немного больше операционной работы.

При очень дешёвых годовых тарифах это часто даёт больший выигрыш, чем покупка одного большого сервера.

### 4.3. Production

```text
┌──────────────────────────────┐
│ Agent sandbox VM             │
│ whole-process isolation      │
│ no production credentials    │
└──────────────────────────────┘

┌──────────────────────────────┐
│ Public application VM        │
│ reverse proxy + API + DB     │
│ no agent shell access        │
└──────────────────────────────┘

┌──────────────────────────────┐
│ Local/on-demand GPU worker   │
│ ComfyUI + models + GPU       │
└───────────────┬──────────────┘
                │
                ▼
       Object storage / B2
       media + immutable backup
```

Такое разделение следует вводить до появления ценных пользовательских данных, платных заказов и production-ключей.

## 5. GreenCloud Budget KVM

### 5.1. Актуальные промотарифы Frankfurt

На дату проверки официальная витрина содержала:

| Тариф | CPU | RAM | Диск | Трафик | Цена |
|---|---:|---:|---:|---:|---:|
| BudgetKVMDE-2 | 2 shared EPYC Rome | 4 ГБ | 35 ГБ NVMe RAID-10 | 4 ТБ | $25/год |
| BudgetKVMDE-3 | 4 shared EPYC Rome | 8 ГБ | 60 ГБ NVMe RAID-10 | 8 ТБ | $45/год |

Оба тарифа включали:

- один IPv4;
- `/64` IPv6;
- порт, обозначенный как 10 Gbps;
- VirtFusion;
- один слот backup/snapshot;
- Linux;
- отсутствие возврата денег.

Наличие меняется динамически, а sale-тариф может исчезнуть до завершения заказа.

### 5.2. Что означает shared CPU и правило 30%

GreenCloud указывает, что CPU обычных KVM shared. Средняя загрузка не должна превышать 30%, а burst до 100% разрешён на короткое время. Длительная нагрузка, влияющая на соседние VPS, может привести к ограничению, перезагрузке, выключению или приостановке сервиса.

Это не означает, что процессор всегда технически ограничен на отметке 30%.

Для 4 vCPU можно использовать грубую планировочную модель:

```text
кратковременно: до 4 vCPU
длительно: workload должен быть в основном idle/bursty
```

Нельзя считать 1,2 vCPU гарантированной выделенной мощностью: провайдер не раскрывает точный алгоритм расчёта среднего.

Подходящие нагрузки:

- AI-агент, ожидающий ответы LLM;
- браузер с короткими всплесками;
- n8n, вызывающий внешние API;
- небольшой backend;
- периодические тесты и сборки;
- очередь GPU-заданий.

Неподходящие нагрузки:

- локальная LLM на CPU;
- постоянное кодирование видео;
- CPU rendering;
- тяжёлый crawler на множестве потоков;
- непрерывный CI;
- многочасовая загрузка всех ядер.

После покупки полезно наблюдать не только обычный CPU, но и `steal time`: высокая величина может указывать на перегруженный физический узел.

### 5.3. Регистрация и antifraud

В одном фактическом процессе регистрации, наблюдавшемся в августе 2026 года:

- отдельная регистрация была отключена, аккаунт создавался во время заказа;
- `Russian Federation` присутствовала в списке стран;
- телефонное поле поддерживало код `+7`;
- обязательная SMS-проверка на этапе создания аккаунта не наблюдалась;
- включённый VPN вызвал ошибку MaxMind;
- после обращения поддержка вручную вернула заказ в состояние Pending;
- иностранную виртуальную карту разрешили использовать после подтверждения скриншотом из приложения управления картой;
- поддержка разрешила скрыть первые восемь цифр номера и остальные чувствительные данные;
- обычный десятипроцентный промокод не применился к Budget KVM Sale.

Это описание одного процесса, а не гарантия для каждого нового клиента.

Официальный FAQ GreenCloud указывает, что новые клиенты при оплате банковской картой или PayPal проходят дополнительную проверку, обычно один раз для карты или аккаунта. Sale-планы могут быть невозвратными.

Практические правила регистрации:

- не использовать VPN или proxy;
- указывать настоящие ФИО, страну, адрес и телефон;
- подтвердить email до оплаты;
- не создавать второй аккаунт после antifraud-ошибки;
- сначала обратиться в поддержку;
- не отправлять полный номер карты, CVV или секретные данные;
- использовать только платёжный инструмент, который можно подтвердить.

### 5.4. Отзывы

Отзывы о GreenCloud полярны. На дату проверки Trustpilot показывал рейтинг около 3,4 из 5 при 121 отзыве: примерно 70% оценок составляли пять звёзд, около 26% — одна звезда.

Положительные отзывы чаще упоминают:

- низкую цену;
- хорошую производительность относительно стоимости;
- быстрые ответы поддержки;
- стабильную работу отдельных локаций.

Негативные отзывы чаще связаны с:

- жёсткими правилами оплаты и возврата;
- заблокированными или проблемными IP;
- packet loss и jitter на отдельных узлах;
- отдельными историями downtime и потери данных.

Отзывы пользователей не являются benchmark. Они подтверждают необходимость внешнего backup и проверки конкретного VPS после покупки.

## 6. Tencent Cloud Lighthouse

### 6.1. Промотариф

На дату проверки Tencent публиковал стартовый пакет:

- 2 vCPU;
- 2 ГБ RAM;
- 40 ГБ SSD;
- до 20 Mbps;
- 0,5 ТБ исходящего трафика в месяц;
- $10.08 за первый год;
- исходная обозначенная цена — $50.40 в год.

Также публиковались обычные Lighthouse-конфигурации, включая 2 vCPU / 4 ГБ / 90 ГБ. Конкретная доступность зависит от аккаунта, региона и checkout.

### 6.2. Для чего подходит 2 ГБ

Подходящие роли:

- небольшой backend;
- Telegram- или иной bot worker;
- PostgreSQL с маленькой БД;
- Caddy;
- несколько статических сайтов;
- monitoring;
- cron;
- utility node;
- аварийная SSH-машина.

Неудачные роли:

- AI-агент с постоянно работающим Chromium;
- локальные модели;
- тяжёлые Docker builds;
- несколько SSR-приложений;
- файловый CDN;
- выдача больших изображений и видео.

### 6.3. Ограничение 20 Mbps

20 Mbps соответствуют теоретическим 2,5 МБ/с.

Оценочное минимальное время передачи:

| Объём | Теоретическое время |
|---:|---:|
| 1 ГБ | 6 минут 40 секунд |
| 10 ГБ | 1 час 7 минут |
| 40 ГБ | 4 часа 27 минут |

Реальная передача будет медленнее из-за TCP, маршрута, шифрования и удалённого сервиса.

Ограничение почти незаметно для:

- SSH;
- API;
- bot traffic;
- Git;
- JSON;
- небольших сайтов;
- мониторинга.

Оно заметно для:

- моделей;
- больших Docker images;
- видео;
- полных архивов;
- файловой раздачи;
- проксирования результатов генерации.

В квоту входит исходящий публичный трафик. Поэтому GPU-worker должен загружать результаты непосредственно в объектное хранилище, а backend — передавать URL и metadata.

### 6.4. Платёжная проверка

Tencent проводит pre-authorization примерно на $1. Официальная документация указывает, что virtual и gift cards не поддерживаются; отдельные debit cards также могут не пройти. Успешная оплата виртуальной картой у другого хостера ничего не гарантирует для Tencent.

## 7. ComfyUI: control plane и GPU worker

Рекомендуемая схема:

```text
CPU-VPS
├── custom node repositories
├── workflow JSON
├── model manifests
├── tests without CUDA
├── API / job dispatcher
└── deployment scripts
          │
          ├─────────► Local GPU worker
          │            └── ComfyUI + models
          │
          └─────────► Cloud GPU worker
                       └── ComfyUI + models
                              │
                              ▼
                        Object storage
```

На CPU-VPS не следует хранить основной набор весов, если диск всего 40–60 ГБ.

Поток выполнения:

1. backend создаёт job;
2. worker получает job через private API или polling;
3. worker запускает workflow в локальном ComfyUI;
4. результат загружается в объектное хранилище;
5. backend получает URL, размер, hash и metadata;
6. временный GPU-worker может быть удалён.

### GPU по требованию

RunPod публиковал ориентиры около $0.34 в час для Community RTX 4090 и примерно $0.69–0.74 в час для Secure Cloud. Оплата идёт по фактическому времени работы.

On-demand GPU обычно выгоднее постоянного сервера, пока загрузка:

- нерегулярна;
- занимает десятки, а не сотни часов;
- может ставиться в очередь;
- допускает запуск worker по необходимости.

Постоянный GPU становится рациональным при стабильной высокой утилизации и предсказуемой выручке.

## 8. n8n

n8n может хранить большое количество чувствительных данных:

- API-ключи;
- bot tokens;
- OAuth refresh tokens;
- доступ к GitHub;
- доступ к Google;
- доступ к объектному хранилищу;
- credentials баз данных;
- webhook secrets.

При совместном размещении с AI-агентом необходимо:

- использовать отдельные контейнеры;
- не создавать общие volumes;
- не передавать агенту `.env` n8n;
- не передавать `N8N_ENCRYPTION_KEY`;
- разделить Docker networks;
- ограничить credentials development-аккаунтами;
- не передавать агенту Docker socket.

validation

## 10. Безопасность AI-агента

### 10.1. Агент не должен видеть production

В агентном контуре не должны находиться:

- SSH private key публичного backend;
- пароль production PostgreSQL;
- production bot token;
- master-key от облака;
- ключ, позволяющий удалить backup;
- credentials CI/CD с прямым production deploy;
- writable mount production-репозитория;
- `/var/run/docker.sock`.

Подключение Docker socket к контейнеру агента фактически позволяет управлять хостовыми контейнерами и часто эквивалентно административному доступу.

### 10.2. Минимальная структура каталогов

```text
/opt/agent/
├── compose.yaml        root-owned
├── config/             read-only for agent
├── workspace/          agent read-write
├── data/               agent read-write
└── host-backup/        unavailable to agent
```

Backup должен запускаться хостом, а не самим агентом.

### 10.3. Контейнерные ограничения

- запуск не от root;
- rootless Docker или Podman;
- read-only filesystem, где возможно;
- лимиты RAM, CPU и PID;
- отдельная network;
- ограничение размера логов;
- запрет privileged mode;
- отсутствие общих volumes;
- отсутствие cloud control-plane credentials.

## 11. Сетевая схема

### Agent VPS

Публичные порты желательно не открывать. SSH, dashboard и admin API доступны через Tailscale.

### Public backend VPS

Наружу открываются:

- `443/tcp`;
- `80/tcp` только для redirect или ACME;
- при необходимости один публичный webhook endpoint.

Не публикуются:

- PostgreSQL;
- Docker API;
- n8n admin UI;
- metrics;
- внутренний GPU API;
- SSH после настройки приватного доступа.

### Tailscale

Рекомендуется использовать tagged auth keys и явные grants:

```text
operator      → agent SSH/UI
operator      → backend SSH/admin

backend       → GPU worker API
GPU worker    → backend callback
GPU worker    → object storage

agent         ✕ backend PostgreSQL
agent         ✕ backend SSH
agent         ✕ cloud control plane
```

Tailscale поддерживает tagged devices, ACL/grants и Tailscale SSH.

## 12. Backup и восстановление

GitHub является backup кода и конфигурации, но не заменяет backup:

- PostgreSQL;
- состояния AI-агента;
- n8n credentials;
- `N8N_ENCRYPTION_KEY`;
- browser profile;
- пользовательских файлов;
- секретов.

Рекомендуемая схема:

```text
host systemd timer
        ↓
pg_dump / tar / restic
        ↓
encryption
        ↓
B2 bucket with Object Lock
```

Разделение buckets:

```text
agent-backup-locked
backend-backup-locked
media-production
gpu-output-staging
```

Application Key для backup должен быть ограничен:

- конкретным bucket;
- при необходимости prefix;
- минимальным набором capabilities;
- без `deleteFiles`;
- без `bypassGovernance`;
- без доступа к другим buckets.

Backblaze Application Keys поддерживают ограничения по bucket, prefix и операциям.

### Object Lock

Начальный безопасный подход:

- Governance;
- retention 7–14 дней;
- uploader без права обхода.

После тестирования восстановления:

- Compliance для наиболее важных backup;
- retention 30 дней;
- отдельные месячные архивы.

Compliance нельзя обойти до окончания retention. Governance может быть обойдён ключом с соответствующим разрешением.

B2 публикует базовую цену около $6.95 за ТБ в месяц.

### Начальные цели

| Компонент | Backup | Цель |
|---|---|---|
| Agent workspace | ежедневно и перед обновлением | потеря не более 24 часов |
| PostgreSQL | `pg_dump -Fc` каждые 6 часов | потеря не более 6 часов |
| n8n database | ежедневно | восстановление workflow и execution state |
| Secrets | отдельно и зашифрованно | не зависеть от VPS |
| Media | сразу в object storage | не зависеть от GPU-worker |
| Provider snapshot | перед крупным изменением | быстрый rollback |
| Restore test | регулярно | проверять восстановление, а не наличие файлов |

## 13. Linux, SSH и базовое администрирование

### 13.1. Операционная система

Для большинства описанных задач рационален:

> **Ubuntu Server 24.04 LTS x86_64**

Полноценный desktop обычно не нужен. Управление возможно через:

- SSH;
- VS Code Remote SSH;
- Windsurf Remote SSH;
- Cockpit;
- Portainer;
- VirtFusion или панель провайдера;
- собственные web-интерфейсы n8n и сервисов.

XFCE, xRDP или NoMachine можно установить позднее, но графический desktop увеличивает потребление RAM, диска и поверхность атаки.

### 13.2. SSH-ключи

Рекомендуемая модель:

- отдельный административный ключ на каждый контур или провайдер;
- private key остаётся на локальной машине;
- public key загружается на VPS;
- passphrase шифрует private key локально;
- пользователь вводит passphrase при подключении либо загружает ключ в `ssh-agent`;
- AI-агент не получает личный admin key;
- для автоматизации создаются отдельные deploy keys;
- passphrase существующего ключа можно поменять без замены public key.

После проверки входа по ключу:

- отключить SSH password authentication;
- запретить прямой root login;
- создать отдельного sudo-пользователя;
- закрыть публичный порт 22 после настройки Tailscale.

### 13.3. TOTP

OTP при настройке приложения-аутентификатора — шестизначный код, обновляющийся по времени.

При ошибке:

1. включить автоматические дату и время;
2. включить автоматический часовой пояс;
3. удалить некорректную запись;
4. запросить новый QR;
5. просканировать его повторно;
6. ввести свежий код сразу после обновления.

QR, seed phrase и recovery codes нельзя пересылать или хранить в открытом виде.

## 14. Платёжные методы и реальная стоимость

Рекламная цена VPS не учитывает:

- выпуск виртуальной карты;
- курсовую наценку;
- комиссию за транзакцию;
- pre-authorization;
- VAT;
- blockchain fee;
- повышение цены после promotion.

### Пример влияния виртуальной карты

В одном наблюдавшемся предложении:

- выпуск карты стоил около 2,3 тыс. ₽;
- предоставлялся бонус $5;
- курс пополнения был около 100,7 ₽/$;
- комиссия составляла $0.25 за операцию.

При оплате сервисов общей номинальной стоимостью около $55 разовая стоимость выпуска увеличивала эффективную цену первого года примерно до 134 ₽ за $1 номинальной стоимости сервисов.

Главный вывод:

> Для небольшой первой покупки стоимость выпуска карты может быть важнее комиссии и курса.

Для последующих платежей, когда выпуск уже оплачен, эффективная стоимость снижается до курса пополнения плюс комиссия за транзакцию.

### Crypto

Преимущества:

- не требуется совпадение cardholder name;
- принимается некоторыми хостерами;
- не нужен иностранный банковский счёт.

Риски:

- crypto не гарантирует отсутствие antifraud или KYC;
- ошибка сети USDT может привести к безвозвратной потере средств;
- требуется учитывать network fee;
- crypto-платежи часто невозвратны.

До покупки криптовалюты необходимо увидеть точную монету, сеть, сумму и срок действия invoice.

### Практические правила оплаты

- сначала получить письменное подтверждение поддержки о виртуальной карте;
- сравнивать эффективный курс, а не только заявленную комиссию;
- учитывать стоимость выпуска карты;
- учитывать pre-authorization;
- сохранять invoice и условия renewal;
- отключать auto-renew до проверки цены продления;
- не использовать фиктивные данные;
- не инициировать chargeback до общения с поддержкой;
- не отправлять CVV и полный номер карты в тикет.

## 16. План внедрения

### Этап 1 — development

1. Выбрать один сервер 4/8 либо пару 4/8 + 2/2.
2. Установить Ubuntu Server 24.04.
3. Настроить SSH-ключи, sudo-пользователя и Tailscale.
4. Включить firewall deny-by-default.
5. Установить Docker или Podman.
6. Разделить сервисы на независимые Compose-проекты.
7. Настроить лимиты контейнеров и ротацию логов.
8. Подключить Git-репозитории без production credentials.
9. Настроить внешний backup.
10. Сделать baseline snapshot.

### Этап 2 — GPU worker

1. Поднять локальный или временный облачный ComfyUI worker.
2. Разместить модели на GPU-машине.
3. Настроить private job API.
4. Загружать результаты напрямую в object storage.
5. Проверить пересоздание worker с нуля.
6. Посчитать стоимость одной генерации.
7. Проверить остановку GPU без потери результата.

### Этап 3 — production

1. Вынести AI-агента на отдельную VM.
2. Удалить production-секреты из development.
3. Ограничить deploy через CI/CD.
4. Усилить Object Lock.
5. Добавить PostgreSQL WAL/PITR при необходимости.
6. Включить alerting по CPU, RAM, swap, disk и uptime.
7. Проверять restore регулярно.
8. Масштабировать только по измеренным метрикам.

```text

4 shared vCPU
8 GB RAM
60 GB NVMe

+

```

- достаточный запас RAM;

Эта схема остаётся development-архитектурой, а не заменой production-инфраструктуры. Перед запуском критичных сервисов необходимо перейти к более предсказуемому провайдеру, усилить backup, исключить production credentials из агентного контура и проверить восстановление из независимой копии.
