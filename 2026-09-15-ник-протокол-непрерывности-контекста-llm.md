# Управление контекстом и непрерывностью задач LLM
## Универсальная архитектура и нормативный протокол исполнения

**Идентификатор:** `LLM-CONTINUITY-IMPL`  
**Редакция:** 1.2  
**Дата:** 15 сентября 2026 года  
**Назначение:** самодостаточная основа для спецификации и реализации в конкретной агентной среде.  
**Профиль ядра:** один владелец исполнительного контекста, последовательная выдача действий, одно долговечное хранилище.  
**Статус:** консолидированная редакция после проверки архитектуры и логических контрпримеров. Соответствие конкретного runtime подтверждается отдельно.

> Задача живёт дольше контекстного окна. Перед управляемой заменой контекста runtime сохраняет и проверяет состояние задачи. После замены он возвращает обязательное состояние модели. Обычная работа разрешается только после проверенного восстановления и повторной проверки полномочий.

**ДОЛЖЕН / НЕЛЬЗЯ** — обязательное правило протокола; **СЛЕДУЕТ** — рекомендуемая реализация; **МОЖЕТ** — опция. Порог 95%, состав состояний и правила допуска — проектные решения этого документа, а не свойства всех моделей или API.

Эта редакция заменяет нормативное поведение спецификации 1.1 и самодостаточно включает необходимую архитектурную основу редакции 2.0. Старые SQL, JSON Schema, FSM, fixtures и closure-файлы не являются приложениями к этому документу и не становятся исправленными автоматически. При использовании старого кода их необходимо привести к настоящему договору и проверить. Трассировка изменений приведена в приложении А.

## 1. Назначение и границы гарантии

Протокол соединяет **Context Budget → Hook → Handoff + Decision Log → Linter → Gate → Compaction → Restore**. Он применяется к локальным и облачным LLM, текстовым и мультимодальным контекстам, инструментальным агентам и диалоговым средам.

**Context rollover** — управляемая замена истории: compaction, пересборка контекста, новая сессия или несовместимая смена модели. **Epoch** — номер принятой версии контекста внутри одного `run_id`; он не равен номеру задачи или сессии провайдера. **Checkpoint / Continuity Bundle** — один логический пакет продолжения; создавать ради него множество файлов не требуется.

Сохраняются цель, ограничения, решения с краткими основаниями, проверенные результаты, неопределённости и безопасный следующий шаг. Скрытые рассуждения модели не запрашиваются и не являются необходимыми данными протокола.

Протокол не заменяет авторизацию, sandbox, резервное копирование ресурсов, долговременную память, планировщик, биллинг или бизнес-логику. Существующие механизмы переиспользуются.

Строгая гарантия относится к **контролируемым исполнительным границам**. Она не доказывает правильность всех выводов LLM, идеальность summary, отсутствие любых prompt injection или exactly-once работу внешнего API. Нельзя гарантировать новый Handoff непосредственно перед аварией питания: для этого случая используются ранее сохранённое состояние и reconciliation — сверка фактических исходов.

### Обязательные инварианты

| ID | Правило |
|---|---|
| I01 | Каноническое состояние задачи и решения существуют вне временного контекста LLM. |
| I02 | Обычное исполнение допускается только в `RUNNING`, при `disposition=ACTIVE`, после admission текущего владельца и с актуальными проверками конкретного действия. |
| I03 | Управляемая замена контекста требует опубликованного, проверенного и актуального checkpoint. |
| I04 | Новый epoch не получает обычные полномочия до восстановления обязательного состояния. |
| I05 | Известные ошибки и UNKNOWN сохраняются честно; они не превращаются в успех или подтверждённую отмену ради прохождения Linter. |
| I06 | Сохранение состояния и разрешение продолжать — разные решения. UNKNOWN может разрешать rollover, но блокировать обычное возобновление. |
| I07 | Один допуск применяется к одной конкретной попытке. Изменение запроса, контекста, полномочий или значимых версий требует нового допуска. |
| I08 | Один transition принимает не более одного результата и увеличивает epoch не более одного раза. |
| I09 | STOP закрывает выдачу новой работы, но не запрещает сохранять результаты и безопасно выяснять исход уже начатого действия. |
| I10 | Служебная смена стадии не делает содержание собственного checkpoint устаревшим. |
| I11 | Все модельные запросы, включая Handoff, repair и Restore, проходят нативные лимиты своего маршрута. Кэш не увеличивает окно. |
| I12 | Повторы, восстановление и подготовка имеют конечные бюджеты. Перезапуск не обнуляет расход. |
| I13 | Модель, Handoff и недоверенные источники не могут назначить себе PASS, изменить Gate или повысить полномочия данных. |
| I14 | Ошибка критической проверки не разрешает защищаемую операцию. Старый callback, permit или сохранённое слово RUNNING не являются разрешением. |

## 2. Минимальная архитектура

Достаточно четырёх логических обязанностей в одном модуле приложения.

| Компонент | Обязанность |
|---|---|
| `RuntimeAdapter` | Фактический маршрут модели, окончательный запрос, измерение, перехваты, вызовы, классификация ответов и сохранение результатов. |
| `ContinuityController` | Контекстный бюджет, пять стадий, Gate, одноразовый допуск, ограниченные повторы и recovery. |
| `CheckpointService` | Каноническое состояние, Decision Log, журнал операций, сборка и атомарная публикация checkpoint. |
| `ContinuityValidator` | Структура, свежесть, обязательные ограничения, evidence, восстановимость и применимость результатов проверок. |

```text
                         LLM
                          │ ответы / предложения действий
                          ▼
                 RuntimeAdapter
                границы исполнения
                          │
                          ▼
               ContinuityController ──────► Tools / API / файлы
                Budget · State · Gate          только после допуска
                    │            │
                    ▼            ▼
           CheckpointService   Validator
                    │            │
                    └──────┬─────┘
                           ▼
              Существующее durable store
          State · Decisions · Operations · Checkpoints
```

**Hook** вызывает обработчик на границе операции. **Linter** выдаёт проверенный результат. **Gate** принимает решение о конкретной операции. **Runtime** физически исполняет запрет. Уведомительный Hook после события не заменяет блокирующий перехват до действия.

Ядро не требует микросервисов, универсального policy DSL, отдельного SDK, векторной БД, очереди собственного производства, распределённых leases или постоянного второго LLM-ревьюера. Несколько логических объектов могут храниться в одной таблице либо существующем агрегате приложения. Необходимы свойства хранения, а не заданное число таблиц.

## 3. Профиль интеграции и точки перехвата

Единица управления — `run_id`, то есть один исполняемый контекст. У него один доверенный владелец и не более одного активного rollover. Развёртывание обеспечивает единственность владельца, например эксклюзивным process lock; запуск второй копии не обходится надеждой на дисциплину вызывающего. Базовая реализация выдаёт действия последовательно. Если в истории присутствуют несколько незавершённых задач, checkpoint охватывает их все раздельно, включая приостановленные обязательства; он не сохраняет только последнюю подзадачу.

Адаптер фиксирует версии runtime, адаптера и маршрута, способ измерения, доступные перехваты, модель durability и известные обходные пути. Режимы:

| Режим | Что означает |
|---|---|
| `OFF` | Протокол не участвует. |
| `SHADOW` | Вычисляет решения и сохраняет диагностику, но не меняет исполнение. |
| `ADVISORY_ONLY` | Даёт инструкции/напоминания при неполной интеграции; строгой гарантии нет. |
| `STRICT` | Проверенные blocking boundaries охватывают все защищаемые действия и управляемые переходы. |

### Минимальные границы

| Граница | Необходимое поведение |
|---|---|
| Перед модельным запросом | Окончательная сборка, профиль, бюджет, режим вызова и допуск. |
| Перед действием инструмента | Полномочия, актуальность входов, одноразовый допуск; журнал намерения до побочного эффекта. |
| После ответа или действия | Долговечная фиксация известного исхода до следующего обычного шага. |
| Перед включением результата в историю | Ограничение размера, статус/ошибки, ссылки, формат call↔result, новый бюджет. |
| Перед любым rollover | Актуальный опубликованный checkpoint; запрет рекурсивного rollover. |
| После rollover и при restart/resume | Обычный Gate закрыт до предусмотренной проверки восстановления. |

Инвентаризация включает ручную, автоматическую, overflow- и server-side compaction, встроенные инструменты провайдера, fallback и автоматические повторы SDK. Недоступный перехват нельзя компенсировать сильнее сформулированным промптом. Встроенный инструмент с автономными побочными эффектами должен быть отключён на служебных вызовах или управляться эквивалентной проверенной границей.

Адаптер должен видеть обязательную часть фактически отправляемого запроса после преобразований host. Для скрытой серверной истории нужны проверяемая привязка к версии контекста и консервативный учёт её размера. Если history может незаметно изменяться, соответствующий маршрут не получает `STRICT`.

## 4. Данные, идентичность и версии

### 4.1. Минимальные логические записи

| Запись | Обязательная информация |
|---|---|
| `RunState` | run/epoch, текущий context handle и его версия, stage, disposition, владелец/boot, controller revision, выбранный checkpoint, активный transition, последнее восстановление, причина блокировки. |
| `TaskState` | task ID, статус, цель, критерии, область, канонические ограничения, рабочее состояние, следующий шаг, task revision. |
| `DecisionRecord` | ID в задаче, формулировка, краткое основание, статус, область, полномочие, версии/ссылки на evidence и заменяющее решение. |
| `OperationRecord` и attempts | Логическое намерение, задача/ресурсы, параметры, исходы и доказательства, история попыток, способ выяснить результат. |
| `Checkpoint` | Неизменяемое тело снимка, content version, source epoch, Handoff, зависимости, validation и публикация. |
| `TransitionRecord` | ID, причина, source epoch/context, target profile, checkpoint, попытки, результаты, выбранный результат и budgets. |
| `RestoreDelivery` | Неизменяемая квитанция контролируемой доставки: checkpoint, epoch, окончательный запрос, профиль/политика и завершённый ответ. |
| `GatePermit` | Одноразовый допуск с включённым `BudgetDecision`, точными привязками и записью момента потребления. |

Run disposition имеет значения **`ACTIVE`, `PAUSED`, `CANCELLED`, `COMPLETED`**. Это намерение управления run, а не подтверждение остановки внешнего процесса. STOP устанавливает PAUSED. CANCEL не превращает уже отправленную операцию в CANCELLED_CONFIRMED. Terminal task не возвращается в активное состояние без нового полномочного изменения задачи. Удалённая отмена не обязательна для ядра: её реализация требует отдельного авторизованного control-контракта и не маскируется под read-only STATUS_QUERY.

### 4.2. Разделение свежести и CAS

Используются разные понятия, которые НЕЛЬЗЯ сводить к одному глобальному счётчику:

| Версия | Что меняет | Для чего используется |
|---|---|---|
| `state_revision` | Стадия, управляющие указатели, владелец, disposition и другие данные контроллера | CAS **текущей короткой транзакции**. |
| `ContentVersion` | Состав задач; task/decision revisions; журнал рабочих операций; версии релевантных ресурсов; применённые полномочные изменения входа | Свежесть содержания checkpoint и восстановленного плана. |
| `context_version` | Изменение фактической истории, включая новые сообщения и служебный вывод | Привязка окончательного запроса и его измерения. |
| `policy/profile/security revisions` | Эффективная политика, маршрут/учёт лимитов, правила доступа и получатели | Применимость проверок и допуска в текущей среде. |

`ContentVersion` может быть одним счётчиком уже существующего task aggregate или вектором его доменных ревизий. Все влияющие изменения обязаны его менять. Новая стадия PREPARING, запись draft, validation, метрика, retry timer и checkpoint pointer **не меняют ContentVersion сами по себе**. Handoff не содержит captured `state_revision` как требование свежести.

Журнал служебных попыток не смешивается с версией журнала **рабочих** операций. Полученный результат рабочей операции или reconciliation, меняющий известное состояние мира, меняет ContentVersion. Сам факт выполнения status-query без новых сведений — нет.

Пример:

```text
capture: ContentVersion=27, state_revision=100
служебные build/validate: state_revision=103, ContentVersion=27
publish: содержание актуально; CAS выполняется с ожидаемой revision=103

изменено ограничение задачи: ContentVersion=28
старый draft для 27 больше не пригоден к публикации
```

Для входа отдельно хранятся `received_watermark` и `applied_watermark`. Перед публикацией, отправкой, Restore-resume применяются все уже принятые значимые события до зафиксированной границы. Новое событие после этой границы инвалидирует связанные непотреблённые допуски. STOP сериализуется с допуском отправки (§7.4).

### 4.3. Идентификаторы и неизменяемые объекты

ID непустые, уникальные в явно указанной области. Связи всегда проверяют run/task ownership, а при нескольких владельцах данных — также tenant/security scope. UUID подходит, но конкретный генератор не предписан.

На JSON-границах epoch, revisions и монотонные counters передаются строками: `"0"` либо последовательностью десятичных цифр без ведущего нуля; диапазон `0..2^63−1` проверяется до преобразования. Token/byte counts — неотрицательные целые точного диапазона `0..2^53−1`. Boolean не принимается как число. Overflow, NaN, отрицательное значение, неизвестная единица или дубликат ключа — ошибка, а не ноль.

Для переносимых JSON-тел используется RFC 8785 JCS и SHA-256; проверенная библиотека предпочтительнее собственной канонизации. JCS не заменяет проверку входных типов и диапазонов. [S1]

```text
body_hash = SHA256(UTF8(JCS(body)))
Envelope = { body, body_hash, validation_id, published_at }
```

В тело не входят его собственный hash, validation ID или metadata публикации. Validation ссылается на существующие draft ID/hash; envelope создаётся после PASS. Для окончательного запроса hash хранится снаружи запроса. Неизменяемый body никогда не «исправляется на месте»: изменение создаёт новую версию и новую validation.

## 5. Контекстный бюджет конкретной модели

### 5.1. Единственный профиль лимитов

`ModelProfile` идентифицирует фактические provider/route/model revision, runtime-конфигурацию, токенизатор/правило учёта, источник лимитов, время проверки и срок пригодности. Настройка окна или маркетинговое название сами по себе не подтверждают ёмкость.

Единственное численное представление нативных лимитов — `limits[]`. Каждый элемент содержит:

```text
id; metric_id; unit; maximum; comparator (LE или LT);
reserve; measurement_margin; accounting_rule_id; evidence_ref
```

`metric_id` различает вход, общий контекст, генерацию, reasoning, число изображений, байты запроса и другие действительно ограниченные величины. Источник и правило учёта задают, включены ли reasoning и внутренние резервы в другие величины. Один запас и один элемент контекста не учитываются дважды.

Для каждой dimension рассчитывается `upper_usage = measured_or_predicted + measurement_margin`, затем сравнивается с `maximum − reserve` по её comparator. Все применимые dimensions должны пройти. Неизвестное значение допускается только при проверенной консервативной верхней оценке. Непригодный профиль блокирует запрос; другой профиль не подставляется молча.

В модели профиля нет второй независимой копии `native_limits`. Если runtime отдаёт несколько источников, адаптер сначала разрешает расхождения и публикует один эффективный профиль с происхождением. Все изменения effective values создают новую profile revision.

### 5.2. Что измерять

Считается окончательный запрос: инструкции, схемы инструментов, история по значению или серверной ссылке, изображения/аудио, Handoff и обязательные решения. Сумма оплаченных токенов за сессию и предыдущий usage не равны размеру следующего входа. Кэшированные токены не вычитаются.

Запрос после измерения замораживается. Поздняя инъекция tool result, смена tool schema, output limit, route или host transformation требует новой сборки, fingerprint и допуска. Проверка маленького JSON с `previous_context_id` должна учитывать и содержимое/версию контекста за этой ссылкой.

### 5.3. Порог 95% и ранняя подготовка

Для **общего окна вход + выход** используется опорный расчёт:

```text
C       = допустимая ёмкость общего окна из limits[] после его reserve
U       = верхняя оценка текущего входа, включая погрешность
D_next  = дополнительный ограниченный input до следующей проверки
O_next  = реально установленный максимум генерации этого шага
R_save  = пиковый дополнительный ЖИВОЙ контекст пути сохранения

B_stop  = floor(19 × C / 20)
B_start = B_stop − R_save
P_next  = U + D_next + O_next

NORMAL_BUDGET_OK ⇔ U < B_start AND P_next < B_start
```

C выводится из dimension общего окна: `maximum − reserve` для LE, на один токен меньше для LT. Погрешность уже входит в U. Таким образом, 95% относится к подтверждённому рабочему бюджету окна, а не к рекламному максимуму; более строгий нативный предел не обходится. Все остальные dimensions проверяются независимо.

Равенство на B_start/B_stop не допускает обычный шаг. При непрохождении допустимо один раз уменьшить **реальные** границы шага/вывода и пересчитать; иначе начинается PREPARING. Снижать только оценку без изменения исполнения нельзя.

95% — последний барьер обычной работы. Handoff начинается раньше, с резервом, и готовый checkpoint используется сразу: ждать 95% не требуется. Профиль с `B_start ≤ 0` непригоден. Все вычисления целочисленные с проверкой переполнения.

`R_save` включает пиковый рост от Handoff, короткой диагностики, разрешённого repair и требований перехода. Это **не сумма повторно оплаченных input tokens**. Отдельная вспомогательная модель имеет свой входной бюджет; её весь input не прибавляется к исходному контексту, если он туда не внедряется. R_save может быть нулевым только при проверенном детерминированном пути, который не добавляет контент в исходное окно.

| C | Пример R_save | B_start | B_stop |
|---:|---:|---:|---:|
| 65 536 | 8 192 | 54 067 | 62 259 |
| 131 072 | 8 192 | 116 326 | 124 518 |
| 262 144 | 16 384 | 232 652 | 249 036 |
| 1 048 576 | 32 768 | 963 379 | 996 147 |

Это иллюстрации, не пресеты. При `C=65 536`, `U=50 000`, `D_next=1 000`, `O_next=4 096` прогноз равен 55 096: данный шаг уже требует уменьшения либо PREPARING.

Для input-only лимита нельзя сравнивать `input + output` с пределом одного входа. Адаптер отдельно проверяет текущий output limit и прогноз входа после сохранения ответа. Привязочная спецификация должна определить метрику давления, её projection и резерв в той же единице. Несопоставимые метрики нельзя объединять через `min()`.

### 5.4. Нативная compaction

Typed mapping хранится отдельно от нативных лимитов:

```text
NativeCompaction {
  mode: ABSENT | DISABLED | CONTROLLED | UNCONTROLLED,
  triggers: [{ metric_id, unit, threshold, margin, save_growth,
               observation_boundary, blocking_intercept_ref }]
}
```

Для активного порога `safe_start = threshold − margin − save_growth`. В соответствующей метрике прогноз обычного шага должен быть **меньше** safe_start. Единицы, место измерения и bound сохранения обязаны быть совместимы. Параметры trigger являются полями договора, а не неописанными extensions.

UNCONTROLLED или неизвестная метрика без upper bound исключают `STRICT`. Compaction во время Handoff/repair не запускает вложенный rollover: управляемый compactor удерживается координатором. Служебный вызов по-прежнему проходит свои реальные нативные лимиты.

### 5.5. Бюджеты служебных операций

Одна `ContinuityPolicy` содержит пределы, а один `TransitionBudget` — израсходованные counters конкретного перехода. Per-service entry задаёт применимые `max_input_tokens`, `max_output_tokens`, `max_live_growth`, `max_response_bytes`, `max_attempts`, `timeout_ms`; общий budget задаёт persisted deadline и суммарный расход модельных токенов. Для немодельной операции token-поля не применяются явно, а не означают неограниченный LLM-вызов.

По умолчанию: не более одного Handoff-вызова и одного содержательного repair; отдельного ACK-вызова нет. Лимиты status/transition/Restore конечны и задаются до начала соответствующих попыток. Точные значения зависят от runtime, а не от произвольного общего числа.

Перед отправкой атомарно резервируются попытка и верхняя стоимость. При подтверждённом меньшем расходе допустимо сверить резерв с фактическим, сохранив историю; неизвестный расход остаётся зарезервированным. Новый attempt получает новый допуск. Дубликат события не расходует попытку повторно. Deadline не продлевается restart или backoff.

Reconciliation после истечения бюджета перехода использует отдельный небольшой `RecoveryBudget` для status/read-only, а не обнуление старого TransitionBudget. Оператор может явно расширить лимит новой записью с основанием; израсходованные counters сохраняются.

### 5.6. Полезное продолжение и аварийное переполнение

До перехода оценивается, а после восстановительного ответа повторно проверяется: **полный восстановленный контекст + один полезный ограниченный шаг + следующий R_save** помещаются ниже B_stop и всех применимых нативных порогов.

В послевосстановительном расчёте `U_after_restore` уже включает сохраняемую часть ответа Restore. O_restore повторно к нему не прибавляется. Для общего окна:

```text
U_after_restore + D_useful + O_useful + R_save_target < B_stop_target
```

Если проверка не проходит, удаляется только необязательный материал, уменьшается реальный шаг, дробится задача или выбирается подходящий разрешённый профиль. Те же payload/profile не отправляются в бесконечную compaction без прогресса.

Отказ в бюджете **обычного** запроса не запрещает детерминированно сохранить состояние. На уже переполненном окне запрещён повтор того же непомещающегося запроса; можно подготовить checkpoint без LLM и построить чистый контекст. Если обязательных данных недостаточно или они не сохраняются — BLOCKED.

## 6. Decision Log, Handoff и проверяемый checkpoint

### 6.1. Решения фиксируются по мере принятия

Decision Log содержит существенные решения, а не каждое чтение файла. Статусы: `PROPOSED`, `ACCEPTED`, `REJECTED`, `SUPERSEDED`. Изменение решения сохраняет историю и ссылку на замену. Принятое решение имеет подтверждённое полномочие в пределах задачи; предложение модели не становится пользовательским одобрением.

Минимум записи — ID, контекст/основание, решение, статус и последствия для дальнейших шагов. Это соответствует практике небольших ADR, но не требует отдельного документа на каждый технический выбор. [S2]

Перед checkpoint выполняется flush до конкретной ревизии: каноническое состояние и доступные записи согласованы. Отсутствие новых решений сохраняет прежнюю ревизию; пустые или выдуманные решения не нужны. Flush не доказывает отсутствие любого незафиксированного смысла в разговоре.

### 6.2. Тело checkpoint

| Группа | Что сохраняется |
|---|---|
| Identity | schema version, checkpoint/run IDs, source epoch, ContentVersion, охваченные задачи. |
| Task snapshots | Цели, критерии, область, запреты, существенные числа с единицами, прогресс, ошибки и неизвестное. |
| Handoff | Краткое объяснение состояния; выполненное и незавершённое; следующий шаг, его входы, предусловия и проверка результата. |
| Decisions | Ревизии журналов, активные общие ограничения-решения и решения для ближайшего шага; ссылки на остальное. |
| Operations | ID начатых операций, известный исход, effect evidence, затронутые ресурсы и план reconciliation. |
| Resources/evidence | Ссылки, версии, доступность, происхождение; что именно доказано, для какой версии; способ восстановления незаменимых данных. |
| Restore plan | Обязательное содержимое нового запроса, допустимые получатели, материалы по запросу, необходимость сверки до работы. |

`HANDOFF.md` — представление этого тела, а не независимый источник истины. Runtime собирает идентификаторы, статусы, версии и результаты. LLM может формулировать narrative и предложить следующий шаг, но не редактировать защищённые ограничения, выдавать полномочия или назначать результат validation.

Подтверждённое, сообщённое источником, предположение и UNKNOWN различаются явно. Процент готовности не заменяет список проверенных результатов. Падающие тесты допустимы в пригодном checkpoint, если ошибка честно записана и следующий шаг безопасен.

Критическое ограничение хранится в канонической форме. Отрицание, целевой ресурс, предел суммы, единица измерения и запрет публикации не заменяются свободным пересказом. Неясная применимость важного решения требует сохранения или уточнения, а не молчаливого исключения.

### 6.3. Пригодность и Linter

Linter возвращает immutable `ValidationReport`:

```text
validation_id; validator_version; target_id; body_hash;
ContentVersion; policy/profile/security bindings;
result: PASS | BLOCK;
transition_eligible: boolean;
resume_blockers: [typed reasons]; errors[]; warnings[]
```

`resume_eligible=true` не записывается в checkpoint как бессрочное разрешение: условия возобновления проверяются заново в §11. Проверка Linter включает:

| Проверка | Что блокирует пригодность |
|---|---|
| Структура и ownership | Неизвестная обязательная схема, неверные типы, другой run/task, повреждённый hash. |
| Полнота состояния | Потерянная охваченная задача, обязательное ограничение, действующее решение или начатая операция. |
| Утверждения | «Подтверждённый успех» без подходящего evidence; старый результат теста выдан за новый. |
| Свежесть | ContentVersion/релевантная зависимость изменились после сбора. |
| Продолжение | Нет безопасного следующего шага либо честного указания, что требуется оператор. |
| Восстановимость | Критический незаменимый материал исчезнет после перехода и не имеет разрешённой durable copy или доказанного способа восстановления. |
| Получатель и безопасность | Нарушение доступа/передачи, секрет в содержимом, потерянное происхождение, попытка повысить authority. |
| Бюджет | Не помещаются обязательный payload и предусмотренный безопасный путь восстановления/продолжения. |

Полнота проверяется относительно канонических данных и доступных фактов. Linter не способен автоматически доказать, что ни одна важная мысль никогда не была пропущена. Дополнительное содержательное ревью применяется по риску, а не обязательно на каждом цикле.

### 6.4. UNKNOWN не запрещает спасение контекста

Checkpoint может быть `PASS, transition_eligible=true` при UNKNOWN, если сохранены ID, доступные факты, ограничения на повтор и реальный путь status/reconciliation либо явное ожидание оператора. Обычный Gate после Restore остаётся закрыт.

Для такого пакета допускается вместо обычного полезного шага запланировать полезный **ограниченный recovery-шаг**. После его выполнения обычное возобновление всё равно требует отдельной проверки полезного NORMAL-шага. Если даже recovery не помещается, сохраняется аварийный снимок без заявления о возможности модельного продолжения, и run остаётся BLOCKED.

Ссылка/хэш файла не являются backup. Для кода учитываются относящиеся к задаче dirty и untracked files, не только HEAD. Для иных задач — версии соответствующих объектов. Не требуется повторно хэшировать всё окружение или запускать полный тестовый набор при каждом rollover.

## 7. Gate и одноразовый допуск

### 7.1. Классы операций

Класс назначается доверенным runtime по реальной операции, а не по фразе модели «это для Handoff».

| Класс | Допустимые стадии | Дополнительные условия |
|---|---|---|
| `NORMAL_MODEL`, `NORMAL_ACTION` | RUNNING | ACTIVE, current boot admission, нет блокирующих неопределённостей, актуальны полномочия/бюджет/предусловия. |
| `HANDOFF_MODEL`, `REPAIR_MODEL` | PREPARING | ACTIVE, подходящая незавершённая работа подготовки, service budget, инструменты с обычными эффектами отключены. |
| `CONTEXT_TRANSITION` | TRANSITIONING | ACTIVE, опубликованный актуальный checkpoint, подготовленная попытка, совместимый разрешённый маршрут. |
| `RESTORE_MODEL` | RESTORING | ACTIVE, проверенный обязательный payload, service budget; кандидаты действий удерживаются. |
| `STATUS_QUERY`, `RECOVERY_READ` | Любая стадия | Только узкая сверка конкретной существующей операции/зависимости, действующий доступ и RecoveryBudget. Не требует ACTIVE или открытого normal Gate. |
| `LOCAL_CONTINUITY` | Любая стадия | Узкое чтение/сохранение состояния, validation, применение наблюдений и диагностика. Нельзя менять рабочий код/ресурсы под этим классом. |
| `OPERATOR_CONTROL` | Любая стадия | Проверенное полномочие; STOP/CANCEL/RESUME/коррекция/расширение бюджета журналируются. |

`RESULT_INJECTION` — изменение истории, не внешняя отправка. Оно выполняется только доверенным адаптером, в разрешённый context handle и с новой context_version. В RUNNING допускается bounded injection с проверкой давления; в PREPARING/RESTORING — только необходимый служебный материал в их бюджетах. В TRANSITIONING/BLOCKED результат сохраняется вне истории до выбора допустимого контекста.

STATUS_QUERY не освобождён от доступа, сетевых ограничений, лимитов размера и времени. Истёкший бюджет compaction или неизвестное окно LLM не запрещают немодельный status-query. Его маршрут и секреты связываются с исходной операцией; ему не нужен фиктивный модельный BudgetDecision.

Если наблюдение уже пришло, сохранение разрешённых фактов и обновление исхода операции не расходуют новую внешнюю попытку. Исчерпание retry budget не является основанием отбросить поздний результат.

### 7.2. Что связано с допуском

`GatePermit` имеет статусы `ISSUED`, `CONSUMED`, `INVALIDATED`. В базовом профиле его неизменяемое тело включает `BudgetDecision`: отдельный независимо переиспользуемый lifecycle для budget не нужен.

Привязки допуска: run, epoch, owner/boot, operation class, attempt/intent, точный request fingerprint, context handle/version, ожидаемая controller revision, relevant ContentVersion, authority scope, актуальные policy/security и — для модельного запроса или перехода — route/profile/host-transform/execution-limits. Неприменимые поля отсутствуют по контракту класса, а не игнорируются произвольно.

Для model request fingerprint охватывает полный семантический запрос и версию серверной истории. Auth-значения не сохраняются: используются защищённые credential references и их область полномочий. Секретный транспортный заголовок не превращается в открытый audit payload.

`BudgetDecision` содержит decision ID, class, exact request binding, профиль/политику, измерения и результат `ALLOW_NORMAL`, `START_PREPARING`, `SERVICE_ONLY` или `BLOCK`. Только ALLOW_NORMAL может поддержать NORMAL-допуск. SERVICE_ONLY разрешает только указанный служебный класс.

Один decision ID может принадлежать не более одному permit. Если существующая реализация хранит budget и permit раздельно, обязательны UNIQUE-связь и совместное атомарное потребление обоих. Новый permit на старый decision запрещён независимо от того, изменились ли параметры.

### 7.3. Атомарная подготовка отправки

Одна короткая транзакция `prepare_dispatch`:

```text
1. Проверить ownership, current boot и ожидаемую state_revision.
2. Применить уже полученные значимые события; проверить disposition.
3. Проверить класс, exact request/context bindings и нужные версии.
4. Вычислить guard из реальных данных, включая актуальность budget.
5. CAS permit ISSUED → CONSUMED; обеспечить уникальность decision/attempt.
6. Создать attempt PREPARED и зарезервировать его лимиты.
7. Сохранить immutable admission evidence: что проверено и какие версии были текущими.
8. Зафиксировать транзакцию; только затем разрешить adapter отправку.
```

При несовпадении не создаётся частично подготовленная отправка. Само создание attempt/state_revision в этой транзакции не инвалидирует её результат: guard применяется к состоянию **до её эффектов**. Повторный consume даёт отказ. Потреблённый permit нельзя вернуть в ISSUED после timeout.

Для немедленного синхронного исполнения issue и consume могут происходить в одной транзакции. Не нужна отдельная очередь permit. Авторизацию, проверку и отправку должен связывать один контролируемый dispatcher; произвольная отложенная отправка подготовленного payload недопустима.

### 7.4. Граница STOP и внешнего эффекта

STOP и подготовка dispatch сериализуются одним владельцем. Если STOP принят **до точки допуска отправки**, отправка запрещена. Если допуск уже зафиксирован и управление передано отправляющему адаптеру, операция считается потенциально отправленной; протокол не обещает отменить сетевой пакет или уже начавшийся эффект. При возможности адаптер подавляет ещё не отправленный вызов, но отсутствие эффекта требует evidence.

После STOP: disposition=PAUSED, обычный Gate закрыт, непотреблённые permits недействительны, новые Handoff/transition/Restore LLM-вызовы не запускаются. Уже полученные результаты сохраняются, read-only reconciliation разрешено. CANCEL аналогичен, но задаёт CANCELLED; завершённость каждого внешнего действия устанавливается отдельно.

RESUME может перевести PAUSED в ACTIVE только после проверки полномочия; затем используется путь PREPARING/RESTORING по состоянию run. При recovery активного run снимаются только причины блокировки, устранение которых подтверждено. CANCELLED/COMPLETED не оживляются одним техническим retry: требуется новая полномочная постановка или новый run. Оно не восстанавливает старые permits или отозванные approvals. Политика безопасности может дополнительно запретить STATUS_QUERY при отзыве доступа; в таком случае исход остаётся неизвестным, но не объявляется отменённым.

## 8. Единый конечный автомат

Публичных стадий ровно пять: **RUNNING, PREPARING, TRANSITIONING, RESTORING, BLOCKED**. Draft, validated, published, retry-wait и delivered — свойства записей/работы внутри стадии, не самостоятельные разрешающие состояния.

**Единственный владелец следующей стадии — таблица ниже.** Action-функции применяют данные перехода, но не задают альтернативный next stage. Диагностическая phase может быть вычисляемой; вводить второй нормативный автомат substates не требуется.

### Таблица переходов

Приоритет: полномочные STOP/CANCEL; критический отказ среды; учёт результата уже начатого действия; остальные подходящие события. Неизвестное событие не даёт разрешения: оно отклоняется и журналируется. Не каждое невалидное предложение модели переводит весь run в BLOCKED; критическое повреждение состояния или неконтролируемая compaction — переводит.

| ID | Исходная стадия | Событие и проверяемое условие | Следующая стадия | Данные, фиксируемые атомарно |
|---|---|---|---|---|
| F01 | RUNNING | Давление/ручной rollover/несовместимая смена модели; ACTIVE, нет второго transition | PREPARING | Новый transition ID, бюджет, source epoch; обычный допуск закрыт. |
| F02 | PREPARING | Сборка, flush, validation, repair или публикация | PREPARING | Результат шага; публикация только по §9. Не создаётся второй transition. |
| F03 | PREPARING | Актуальный опубликованный checkpoint; ACTIVE; переход разрешён | TRANSITIONING | Зафиксировать план перехода и ссылку на checkpoint. Внешняя отправка ещё не разрешена. |
| F04 | TRANSITIONING | Результат успешен и совпадает с активным transition/source epoch; winner отсутствует; ACTIVE | RESTORING | Выбор результата, новый context handle, epoch+1, restore ещё не выполнен. |
| F05 | TRANSITIONING | Неизвестный исход; ещё доступны безопасные status-запросы | TRANSITIONING | UNKNOWN, status evidence и counters; никакой обычной работы. |
| F06 | TRANSITIONING | Доказан no-effect либо разрешён безопасный повтор; бюджет есть | TRANSITIONING | retry_not_before. По таймеру ожидание снимается; следующая попытка получает новый ID. |
| F07 | RESTORING | Сборка payload, завершённый запрос или разрешённый повтор | RESTORING | Payload/attempt/Delivery, counters; нормальные действия удержаны. |
| F08 | RESTORING | Изменился ContentVersion или reconciliation дал новые факты | RESTORING | Новый descendant checkpoint, новая validation и payload; epoch не меняется. |
| F09 | RESTORING | Все guards возобновления §11 выполнены; ACTIVE | RUNNING | Immutable GateResume + текущее восстановление; старые кандидаты не получают blanket permit. |
| F10 | Любая | Полномочный STOP/CANCEL или завершение run | BLOCKED | disposition PAUSED/CANCELLED/COMPLETED; issued permits invalidated; незавершённые исходы сохранены. |
| F11 | Любая | Критическая ошибка, неконтролируемый переход или исчерпан необходимый бюджет без безопасного пути | BLOCKED | Причина, закрытый допуск, доступное диагностическое состояние. |
| F12 | BLOCKED | Поздний успешный результат активного transition, source epoch совпадает, winner нет; ACTIVE | RESTORING | То же атомарное принятие, что F04; повторного provider call нет. |
| F13 | BLOCKED | Такой же результат, но disposition не ACTIVE | BLOCKED | Принять результат/epoch однократно при допустимости сохранения и выбора target context; disposition не менять; Restore не отправлять. |
| F14 | BLOCKED | ACTIVE после проверки recovery/RESUME; контекст уже принят или можно безопасно восстановить тот же epoch | RESTORING | Текущий admission, выбранное состояние; новый epoch без перехода не создаётся. |
| F15 | BLOCKED | ACTIVE после проверки recovery/RESUME; требуется новый контекст, старый неизвестный transition учтён/изолирован | PREPARING | Продолжить прежний непринятый transition либо явно закрыть его и создать новый; не два активных. |
| F16 | Любая | Повтор уже применённого события или второй результат принятого transition | Та же | Idempotent no-op либо late evidence; epoch, permits и budgets не возобновляются. |
| F17 | RUNNING | Совместимая смена профиля без замены истории, всё проверено | RUNNING | Новая profile revision; измерения и issued permits пересоздаются. |

F03 — локальный вход в TRANSITIONING без provider call. Только после него `prepare_dispatch` создаёт и допускает конкретную попытку по правилам этого класса. Это устраняет зависимость «допуск требует стадию, а вход в стадию требует уже выданный допуск». Между F03 и отправкой checkpoint и полномочия проверяются заново.

F13 не разрешает хранить данные вопреки отозванной политике: при запрете сохранения native result записывается только разрешённое наблюдение об исходе, и run остаётся BLOCKED без активирования этого контекста.

Ни одного обычного пути `BLOCKED → RUNNING` нет. Таймер не открывает Gate; retry меняет готовность **следующей служебной попытки**, а не результат проверки. Исчерпание бюджета ведёт в F11, не к новой бесплатной итерации.

```text
RUNNING
   │ прогноз бюджета / запрос перехода
   ▼
PREPARING: остановить выдачу → учесть операции → flush → Handoff → Linter
   │ актуальный checkpoint опубликован
   ▼
TRANSITIONING: подготовить попытку → compact / clean context → принять результат
   │ epoch + 1, обычный Gate закрыт
   ▼
RESTORING: внедрить обязательное → получить полный ответ → сверить состояние
   │ все guards выполнены
   ▼
RUNNING: каждый следующий шаг имеет собственный свежий допуск

Любая критическая ошибка / STOP → BLOCKED
BLOCKED → только предусмотренное сохранение, status и recovery
```

## 9. Четыре критические транзакции

Сеть и файловая система не включаются в локальную ACID-транзакцию по факту их упоминания в ней. Внешние вызовы выполняются вне коротких транзакций; заранее сохраняются намерение и correlation ID. Атомарная фиксация защищает локальное состояние в пределах проверенной durability-модели. [S3]

### 9.1. `publish_checkpoint`

Проверить точный draft/body_hash, PASS, transition eligibility, полномочия и текущий ContentVersion. Проверить доступность критических зависимостей. В одной транзакции вставить immutable body/validation binding/publication и сменить selected checkpoint через CAS текущей controller revision. Publication не изменяет тело. Читатель видит предыдущий целый checkpoint либо новый целый checkpoint.

При изменении рабочих данных пересобирается draft. При изменении только controller revision повторяется текущий CAS/read, а не весь LLM-Handoff. При смене политики повторяется затронутая validation; прежний body может оставаться исторически неизменным.

### 9.2. `prepare_dispatch`

Использует §7.3 для model/tool/transition attempts: точный запрос, полные применимые bindings, свежий budget, одноразовость, durable reservation и attempt до внешнего вызова. Если budget хранится отдельно, оба объекта погашаются одной транзакцией. Новый attempt не наследует старый permit.

### 9.3. `accept_transition_result`

Проверить run, active transition, source epoch/context, принадлежность результата подготовленной попытке, допустимость native format и отсутствие winner. CAS по **текущей** controller/transition revision выбирает один результат. В той же транзакции устанавливаются target context, epoch=source+1 и стадия F04/F12/F13.

Проверка не требует, чтобы controller revision навсегда совпадала с revision перед отправкой: status-query и STOP могли законно её изменить. Важные изменения задачи не превращают реально успешную compaction в «не было»: исход записывается, а Restore строится с обновлённым состоянием. Отзыв доступа/несовместимый результат может запретить активацию; это не стирает факт внешнего исхода.

UNIQUE `(run_id, target_epoch)` и один winner на transition либо их транзакционный эквивалент запрещают двойное принятие. Повтор того же принятого result ID возвращает тот же факт, не увеличивает epoch. Второй результат сохраняется как late evidence без активации.

### 9.4. `complete_restore`

Прочитать immutable Delivery, её запрос/контекст/профиль и текущие доменные данные. Применить полученные полномочные события; вычислить все guards §11. Только при успехе в одной CAS-транзакции записать GateResume, завершить активный transition (если он есть), очистить его активный указатель и перейти RESTORING→RUNNING. История transition и winner сохраняется. При повторном resume того же факта второй переход не создаётся. Если валидация/полномочия изменились, ранее выданный отказ не превращается в разрешение только из-за очищенного указателя.

Delivery не удаляется и не объявляется «никогда не существовавшей», если позднее изменился ContentVersion. Она остаётся историческим фактом; её **применимость сейчас** закончилась. Для продолжения нужен обновлённый Restore, а не изменение истории доказательств.

## 10. Рабочие операции, неизвестные исходы и повторы

### 10.1. Один договор исходов

Подготовка dispatch и итог операции — разные поля. Attempt содержит `dispatch_state=PREPARED|SENT|NOT_SENT_PROVEN`, outcome, evidence и время наблюдения. PREPARED после crash означает «могло быть отправлено», пока не доказано обратное.

Ниже — единственный нормативный enum outcome для записи, сериализации и хранения. Derived SQL CHECK и Schema должны принимать все эти значения.

| Outcome | Смысл и допустимое действие |
|---|---|
| `PENDING` | Ожидается наблюдение. Следующий обычный шаг не выдаётся до учёта результата. |
| `IN_FLIGHT` | Исполнение подтверждённо продолжается. Не дублировать. Можно сохранить учтённое состояние для rollover. |
| `SUCCEEDED` | Успех подтверждён evidence; учесть результат, не повторять тот же intent как новую работу. |
| `FAILED_NO_EFFECT_CONFIRMED` | Неудача и отсутствие эффектов доказаны. Ограниченный retry возможен при новых актуальных проверках. |
| `CANCELLED_CONFIRMED` | Исполнение остановлено и отсутствие эффектов доказано. Это не просто отправленная команда cancel. Повтор возможен только при действующем намерении и разрешении. |
| `FAILED_WITH_EFFECT` | Ошибка с известным частичным/полным эффектом. Сохранить полученное состояние; повтор не является автоматически безопасным. |
| `UNKNOWN` | Исход или эффект не установлен. Только reconciliation либо специально доказанный безопасный retry. |

Cancel после частичного изменения не выдаётся за CANCELLED_CONFIRMED: используется FAILED_WITH_EFFECT, если изменения установлены, иначе UNKNOWN. Ошибка с возможным эффектом также UNKNOWN до сверки. Неполный модельный ответ не исполняется как законченный tool call.

Outcome и каноническое состояние рабочей операции обновляются одной транзакцией. Опоздавшее менее определённое наблюдение не понижает SUCCEEDED до UNKNOWN. Противоречащие terminal evidence сохраняются и требуют сверки; правило «последний ответ всегда прав» запрещено.

### 10.2. Безопасность retry и актуальность ресурса независимы

Для каждой изменяющей операции проверяются два разных вопроса:

**Повтор:** может ли тот же intent выполниться повторно? Нужны NOT_SENT_PROVEN, доказанное отсутствие эффекта либо проверенный provider idempotency contract для тех же параметров, ключа, области и срока действия. Таймаут не доказывает отсутствие эффекта. [S4]

**Свежесть:** зависит ли корректность изменения от ранее прочитанной версии ресурса? Если да, требуется atomic conditional write/CAS на стороне ресурса или доказанная эквивалентная сериализация. Новый idempotency key не предотвращает перезапись чужого обновления; например, HTTP If-Match решает именно задачу precondition. [S5]

Для append/create без зависимости от старой версии ETag не обязателен. Для локальных файлов эксклюзивное владение или механизм условного изменения задаются адаптером; отдельное чтение hash перед неконтролируемой записью не закрывает промежуток гонки.

Автоматический retry UNKNOWN с побочным эффектом запрещён по умолчанию. Исключение — явно разрешённый `RETRY_SAME_INTENT` в recovery, с доказанной дедупликацией исходного запроса, текущими полномочиями и актуальными предусловиями. Это отдельная попытка, а не STATUS_QUERY. После STOP такой retry запрещён: status/read-only разрешены, новая mutation — нет.

При получении статуса SUCCEEDED или FAILED_WITH_EFFECT данные задачи обновляются и Restore при необходимости пересобирается. Для исправления известного частичного эффекта создаётся новый план и новый intent; он не маскируется под повтор старого запроса.

## 11. Восстановление и разрешение продолжения

### 11.1. Обязательный вход

Runtime сам собирает обязательное состояние, а не просит модель самостоятельно найти файл Handoff. `RestorePayload` содержит:

| Часть | Обязательное содержание |
|---|---|
| Полномочные инструкции | Действующая политика runtime; цель, область и ограничения пользователя с происхождением. |
| Состояние задач | Все незавершённые обязательства run, подтверждённые результаты, известные ошибки и неизвестное. |
| Handoff | Текущая работа, безопасный следующий шаг, входы и способ проверить результат. |
| Решения | Активные решения, необходимые для шага, и обязательные ограничения; не весь исторический журнал. |
| Незавершённые операции | ID, исходы, запреты на повтор, способ выяснения состояния. |
| Источники | Доступные ссылки на остальной материал; критическое правило не заменяется одной ссылкой. |

Набор обязательных элементов и их ID вычисляется из канонического состояния, а не из списка, составленного самой LLM. Требуемое содержимое имеет проверяемые digest/версии. Summary может переформулировать пояснения, но не подменять канонические ограничения. Текст задачи и документы не повышаются до системных полномочий лишь потому, что они важны для продолжения.

Полный Decision Log и большой tool output остаются вне обязательного payload. Дозагрузка разрешена по ссылкам с проверкой доступа и бюджета. Пакет каждый раз собирается из канонических записей, а не только из summary предыдущего summary.

### 11.2. Проверяемая доставка вместо ритуального ACK

Доставка восстановления подтверждается, когда обязательный payload присутствовал в фактически отправленном восстановительном запросе и получен его завершённый, корректно разобранный ответ. `RestoreDelivery` записывает run/epoch, checkpoint ID/hash, ContentVersion, payload ID/hash, список обязательных элементов, профиль/политику, окончательный request fingerprint, входной context handle/version, result ID и полученную версию контекста.

Адаптер проверяет наличие **содержимого**, а не только совпадение списка ID. Проверка выполняется после host transformations и до отправки. При ссылочной server-side истории необходимо подтвердить соответствующую версию ранее загруженного содержимого. Если host может после проверки незаметно обрезать payload, гарантия доставки отсутствует.

Отдельный вызов «подтверди, что прочитал» не обязателен. Первый содержательный запрос в восстановленном контексте выполняется как `RESTORE_MODEL`: модель может предложить следующий шаг, но её инструменты ещё не запускаются. Этот запрос одновременно приносит полезный результат и подтверждает наблюдаемый путь доставки.

Receipt не доказывает внимание или внутреннее понимание модели. Необходимые смысловые проверки ограничиваются наблюдаемым: нет явного нарушения известных ограничений, следующий шаг имеет допустимую область и актуальные входы. Правильность всей последующей работы остаётся предметом обычных проверок задачи.

### 11.3. Реальные guards открытия Gate

`complete_restore` вычисляет конъюнкцию условий из записей и фактического состояния. Поле `all_resume_guards=true`, присланное моделью, fixture или адаптером без проверяемых оснований, не принимается.

| Guard | Проверка |
|---|---|
| G01 | Stage=RESTORING, disposition=ACTIVE, текущий владелец прошёл boot admission, не принят STOP/CANCEL/отзыв разрешения. |
| G02 | Выбранный context handle/epoch принадлежит данному run; transition принят не более одного раза; нет второго неучтённого исполняющего контекста. |
| G03 | Checkpoint опубликован, hash/структура/validation действительны; ContentVersion и доступ к обязательным зависимостям актуальны. |
| G04 | Delivery принадлежит точному run/epoch/checkpoint/payload; обязательные данные присутствовали в окончательном запросе; ответ завершён и отнесён к нему. |
| G05 | Текущая history является известным результатом этого ответа и только учтённых последующих преобразований. Нет скрытой смены контекста или непроверенного добавления данных. |
| G06 | Все принятые значимые события применены до границы resume; обязательства, решения и полномочия не изменились незаметно после сборки payload. |
| G07 | Нет блокирующего PENDING, IN_FLIGHT, UNKNOWN, неучтённого частичного эффекта или противоречивого результата рабочей операции. |
| G08 | Следующий допустимый NORMAL-шаг и его запас на полезную работу помещаются в текущий профиль по §5; немедленная повторная compaction не требуется. |
| G09 | Нет неустранённой ошибки целостности, недоступности критического состояния, истёкшего обязательного бюджета или требуемого вмешательства оператора. |

G07 относится к операциям, затрагивающим последовательную работу данного run. Завершённый failed test или обычная установленная ошибка задачи не равны UNKNOWN: исправление ошибки может быть безопасным следующим шагом. Изолированная фоновая работа требует отдельного профиля расширения (§16), а не молчаливого исключения из G07.

Открытие Gate означает разрешение **снова проверять и выдавать обычные действия**, не безусловное разрешение всех действий из ответа Restore. Для первого и каждого последующего действия нужен новый допуск §7.

### 11.4. Удержание кандидатов действий

Tool calls из восстановительного ответа сохраняются как кандидаты. До `complete_restore` они не исполняются. После него каждый кандидат проверяется по текущим полномочиям, исходным ограничениям, ресурсным версиям и бюджету. При изменении состояния кандидат отбрасывается либо генерируется заново; он не «дожидается», пока Gate случайно откроется.

Незавершённый stream не даёт разрешения выполнить частично полученный tool call. Адаптер либо удерживает такие элементы вне действующей истории, либо оформляет их завершение/отклонение в соответствии с API. Нельзя создавать некорректную последовательность tool-call/result ради продолжения.

### 11.5. Изменение состояния во время Restore

Если цель, решение, рабочий ресурс или исход операции изменился, полученный Delivery остаётся историческим фактом, но перестаёт подходить для resume. Публикуется обновлённый descendant checkpoint и новый payload **в том же epoch**. Не требуется автоматически повторять compaction или заново увеличивать epoch.

Содержание Handoff при этом обновляется детерминированно там, где это возможно. Полный повторный LLM-Handoff не обязателен. Если ограниченный Restore repair не помогает или обязательное состояние не помещается, run переходит в BLOCKED. Бюджет повторов не создаётся заново.

Таймаут Restore с server-side изменением истории требует проверки фактической context version либо изолированного чистого восстановления. Простая повторная отправка того же запроса в неизвестно изменившуюся history не считается тем же проверенным Restore.

### 11.6. Переносимый пакет и нативная compaction

Checkpoint переносим между совместимыми реализациями протокола. Нативный compacted state может быть непрозрачным и непереносимым. Способ передачи его в следующий запрос определяет API-контракт маршрута, а не общий формат Handoff. Например, существуют API с opaque compaction items и требованием сохранять структуру возвращённого окна; сам запрос compaction также ограничен входным окном. [S6]

Непрозрачное состояние не декодируется и не переносится в другую модель без подтверждённой совместимости. Для смены провайдера или несовместимого формата используется переносимый checkpoint и чистый контекст. Оригинальные источники восстановления не удаляются до успешного resume.

## 12. Bootstrap, перезапуск и восстановление после сбоя

### 12.1. Вход в управление

Сохранённое слово RUNNING не открывает Gate после restart. До чтения долговечного состояния процесс находится под закрытым локальным boot fence. Единственный владелец получает новый `boot_id`, проверяет хранилище, профиль, управляющую стадию, текущую history и незавершённые отправки. Непотреблённые permits предыдущего boot недействительны.

Если сохранённый run был RUNNING, он переводится в RESTORING для проверки/восстановления известного контекста; при неопределённости — в BLOCKED. Незавершённая стадия PREPARING/TRANSITIONING/RESTORING восстанавливается с прежними attempt IDs, бюджетами и фактами. Флаг boot admission устанавливается только после этой сверки. Он не открывает обычный Gate: всё ещё действуют стадия и остальные guards.

Новая задача также не требует особого обхода: создаются epoch=0, TaskState и минимальный проверенный checkpoint; run начинает с RESTORING. Первый содержательный запрос может выполнить роль Restore без дополнительного ACK. Epoch не увеличивается только из-за bootstrap.

При подключении к уже наполненной сессии сначала инвентаризируются незавершённые задачи, ограничения, история и операции. Нельзя просто создать пустой Handoff и признать существующую session безопасной. Если история доступна и помещается, выполняется ограниченное восстановление; если требуется её замена — путь PREPARING с проверенным исходным состоянием. При недоступных существенных данных — BLOCKED.

### 12.2. Таблица crash recovery

| Точка сбоя | Действие после restart |
|---|---|
| До durable intent/consume | Внешняя отправка не должна была начаться. Нужен новый допуск после сверки. |
| После consume/PREPARED, до известного результата отправки | Считать потенциально отправленной; status/reconciliation или доказанный безопасный retry, не слепой replay. |
| Во время сборки/validation | Использовать предыдущий опубликованный checkpoint; неполный draft не считать валидным. |
| После записи artifacts, до публикации указателя | Предыдущий checkpoint остаётся выбранным; orphan artifacts можно удалить позднее. |
| После публикации checkpoint | Продолжить тот же transition; не создавать новую задачу или повторный бесплатный бюджет. |
| Compaction могла завершиться, локального winner ещё нет | Запросить исход по operation/attempt ID. Успех принимать из TRANSITIONING или BLOCKED по F04/F12/F13. |
| После принятия результата и epoch+1 | Продолжить RESTORING или остаться BLOCKED при STOP. Не увеличивать epoch второй раз. |
| После Delivery, до resume commit | Перепроверить текущую применимость Delivery и guards; не выполнять удержанные инструменты автоматически. |
| После resume commit, до следующего действия | Boot fence, сверка текущего состояния, новый допуск; старый permit не восстанавливается. |

Получение результата и изменение рабочих записей фиксируются атомарно. Если запись результата не состоялась, следующая работа не выдаётся; фактический исход выясняется повторным наблюдением.

### 12.3. Безопасный fallback

Чистый локальный контекст из checkpoint — допустимый способ продолжения, если нативная compaction недоступна. Это не разрешение обойти validation или доступ к данным.

Если исход прежней transition attempt неизвестен, fallback допустим только при невозможности старого контекста автономно исполнять инструменты и при надёжном fencing его дальнейшей активации. В активном TransitionRecord сохраняются все попытки, но winner выбирается один. Поздний результат проигравшей попытки не становится новым epoch.

Если старый runtime способен продолжить действия без контроля, изоляция не доказана и fallback не разрешается. Нужен оператор либо доработка адаптера. Неопределённость compaction и неопределённость **рабочего побочного эффекта** не смешиваются: первая иногда решается пересозданием изолированного контекста, вторая требует учёта реального мира.

### 12.4. Конечность recovery

Пределы attempts, суммарного расхода, выходных размеров и deadline сохраняются до вызова. После restart пересчитывается оставшееся, а не назначается полный лимит заново. Монотонные часы применяются внутри процесса; сохранённый deadline сверяется с доверенным временем. При непроверяемом откате часов дальнейшие автоматические повторы не разрешаются без консервативного решения или оператора.

Истёкший budget одной операции не блокирует пассивную запись уже пришедшего результата. Для новых status-запросов используется отдельный конечный RecoveryBudget. Расширение оператором создаёт журналируемое решение и новый лимит; прежний расход и неуспешные попытки сохраняются.

Если текущий контекст уже не помещается даже для Handoff, runtime сохраняет детерминированный emergency snapshot из доступного durable state. Он может быть опубликован только с честным результатом validation; отсутствие обязательных фактов не скрывается. Далее — реконструкция из источников в ограниченном чистом контексте либо ожидание оператора. Повтор переполненного запроса запрещён.

## 13. Безопасность, полномочия и внешние изменения

Контроллер, валидатор, политики Gate и authoritative state защищены от произвольной записи агентом. Служебный инструмент «обновить Handoff» принимает ограниченную структуру и работает только в своей области данных. Он не предоставляет shell, произвольные пути, изменение policy, результатов validation или рабочих файлов.

Данные сохраняют **происхождение, уровень доверия и права доступа** после compaction. Подписанный или аутентифицированный источник не обязательно является источником инструкций. Внешний документ остаётся данными; фраза «отключи Gate» внутри него не превращается в команду runtime после summary.

Credentials не помещаются в Handoff, prompt, обычные логи и экспортируемый bundle. Используются защищённые ссылки. Секрет-сканирование — дополнительная проверка, не доказательство отсутствия всех секретов. Если удаление чувствительной части делает состояние недостаточным, это явный blocker или ограничение получателя, а не разрешение исказить факт.

Все ссылочные чтения проходят проверку области пути/URI, прав, версии и ограничений размера. Artifact ID не разрешает обход каталогов, произвольный сетевой доступ или загрузку активного кода. Контрольные суммы доказывают совпадение содержимого, но не его безопасность и не доверенное происхождение.

При смене модели/маршрута повторно проверяется разрешение **передавать данные этому получателю**. Совместимый формат или больший контекст не заменяют такую проверку. Approvals из checkpoint — только ссылки на историю; их текущая область, срок и полномочия проверяются заново.

Публикация checkpoint подтверждает снимок на определённой границе. Она не блокирует весь внешний мир. Перед изменяющим действием проверяются актуальные предусловия ресурса по §10.2. Событие, пришедшее после resume, может снова закрыть или инвалидировать допуск; это штатное поведение, а не нарушение протокола.

## 14. Хранение, совместимость и завершение задачи

### 14.1. Минимальные требования к store

Нужны короткие транзакции/CAS, уникальность критических идентификаторов, долговечный журнал намерений, атомарное принятие winner и неизменяемость опубликованных снимков. Достаточно существующего транзакционного store; физическая схема выводится из объектов §4, а не из количества сущностей предыдущей редакции.

Крупные artifacts можно хранить отдельно: сначала записать и обеспечить требуемую durability содержимого, затем атомарно опубликовать ссылку в store. При сбое до ссылки допускается orphan; ссылка на ещё не существующее критическое содержимое недопустима. Одна операция rename не доказывает стойкость к потере питания на любой файловой системе.

Если backend не даёт общей транзакции для полей протокола, реализация обязана предоставить проверенный эквивалент публикации и принятия результата. Набор отдельно записываемых JSON-файлов без recovery-правил не считается такой реализацией.

### 14.2. Необязательный профиль SQLite

SQLite — один из подходящих вариантов для локального одновладельческого профиля, а не обязательная технология. При использовании `STRICT` минимум — **3.37.0**; декларация совместимости с 3.35 для такой DDL неверна. STRICT не заменяет весь валидатор JSON и допускает определённые преобразования типов без потерь. [S8]

Наличие используемых JSON-функций проверяется при старте на фактическом соединении. Они включены по умолчанию начиная с 3.38.0, но могут зависеть от сборки; один номер версии недостаточен. Также проверяются `foreign_keys`, необходимые CHECK/UNIQUE и фактическая работа rollback. [S9]

Journal mode, synchronous, fsync и расположение файлов выбираются под заявленную durability-модель. Конкретный WAL или универсальный набор PRAGMA здесь не предписаны. Crash/power-loss claims требуют соответствующих проверок на целевой среде, а не только теста завершения процесса. [S3]

### 14.3. Версии форматов

В каждой сохраняемой структуре присутствует schema_version. Неподдерживаемая версия приводит к отказу исполнения, а не к молчаливому игнорированию новых ограничений. Миграция сначала валидирует исходное состояние, создаёт новое представление и сохраняет связь с неизменяемым оригиналом. Старые hash не переписываются под новые данные.

Enum исходов §10.1, стадий §8 и правил Gate §7 имеет по одному источнику. Schema, DDL, сериализатор и fixtures производятся из него либо проверяются на точное соответствие. Нельзя добавлять статус только в JSON, оставляя несовместимый CHECK в storage.

### 14.4. Завершение и retention

Завершённая задача не должна постоянно увеличивать RestorePayload. После фиксации критериев завершения, известных исходов и итоговых artifact references она архивируется. Оставшиеся обязанности или UNKNOWN не исчезают при смене статуса задачи: они сохраняются в run либо явно передаются другому ответственному процессу.

Пока run активен, защищены выбранный checkpoint, его обязательные зависимости, незавершённые transitions/операции и необходимые decisions. Сборка мусора не удаляет то, что ещё нужно для восстановления. После окончания применяются retention и правила удаления чувствительных данных. Для первого выпуска достаточно явных ссылок и простой политики хранения; отдельный GC-сервис не обязателен.

## 15. Качество продолжения, стоимость и cache

Структурно валидный длинный Handoff может быть бесполезен. Практический критерий — следующий исполнитель различает факт/предположение, знает ограничения и может выполнить допустимый шаг без повторного исследования всей задачи. На репрезентативных задачах проверяются пропущенные ограничения, ошибочные повторы действий и достаточность evidence.

Такую оценку не следует имитировать флагом «семантика проверена». Возможны тестовые задачи с ожидаемым состоянием, ручная выборочная проверка или ограниченный LLM-review по риску. Постоянный второй агент, полный запуск тестов проекта на каждом rollover и отдельный ACK не входят в обязательное ядро. Вынесенные записи и целевая дозагрузка — полезная практика управления долгим контекстом, но не замена исполнительным Gates. [S10]

Compaction не обязательно обнуляет весь prompt cache: неизменённый префикс может продолжить переиспользоваться, изменённая часть — нет; конкретный hit зависит от реализации кэша. Кэшированные input tokens по-прежнему учитываются в объёме контекста. [S7]

Для экономики полезны стабильные инструкции, небольшие обязательные payload и детерминированные checkpoints. Не следует откладывать необходимое сохранение ради cache hit. Decisions, checkpoint, outcome и GateResume не хранятся только в cache. Смена модели требует нового измерения независимо от предполагаемого сохранения кэша.

Минимальная телеметрия: run/epoch/stage, причина rollover, профиль и уверенность измерения, прогноз нагрузки, checkpoint/hash, известные blockers, длительность, число попыток, зарезервированный/фактический расход, возраст checkpoint и результаты Restore. Полные чувствительные prompts для этого не нужны.

## 16. Расширения без усложнения ядра

| Расширение | Когда требуется | Дополнительное условие |
|---|---|---|
| Несколько агентов | Действительно параллельные run | Свои контексты, budgets и epochs; parent получает bounded result, не всю history. |
| Общий изменяемый ресурс | Несколько исполнителей могут писать в одно место | Resource-level concurrency/fencing; нельзя полагаться на независимые локальные Gates. |
| Изолированная фоновая работа | Она не должна блокировать основной run | Durable inbox, явные область/ownership и доказанное отсутствие конфликта со снимком. |
| Несколько владельцев одного run | HA/передача ownership | Lease/fencing или транзакционный эквивалент; старый владелец не выдаёт действующие операции. |
| Передача другой системе | Требуется экспорт продолжения | Проверяемые форматы, получатель, права, переносимые artifacts и новый boot admission. |

Без этих сценариев расширения не реализуются. Формат допускает добавление нужных полей, но базовый протокол не требует распределённого оркестратора. Наследование задачи не означает наследование секретов или прежнего разрешения на mutation.

## 17. Приёмка: один набор требований, реальные наблюдения

### 17.1. Что является источником истины

Таблица ниже — нормативный каталог сценариев. Конкретные input fixtures являются его тестовыми примерами, не вторым источником допустимых исходов. Для каждого варианта явно фиксируются начальное состояние, последовательность входных событий, **граница наблюдения** и допустимое конечное состояние.

Например, запрет «внешний dispatch не произошёл» применяется к указанному классу и интервалу: обычное действие не должно проскочить между началом PREPARING и успешным resume. Законный служебный вызов compaction в этом интервале не является NORMAL-dispatch. После намеренно добавленного успешного Restore разрешённый NORMAL-шаг уже не нарушает такой сценарий.

Сопутствующий acceptance manifest может быть сгенерирован из этой таблицы. Если он существует, fixtures должны ссылаться на его правила, а не переопределять их. Любое расхождение нормативных constraints останавливает package verification.

Идентификаторы прежнего каталога сохранены для трассировки; формулировки уточнены настоящей редакцией.

|---|---|---|

| T01 | Разные окна, input-only и combined профили | Все dimensions измерены по правилам целевого маршрута; ни одного общего фиксированного порога tokens. |

| T10 | Каждый ручной/native/overflow/server-side вход в compaction | До первого context transition есть проверенный checkpoint. Между freeze и resume нет NORMAL-dispatch. Рекурсивный переход блокируется. |
| T11 | Дубли, поздние результаты, старый epoch | Не более одного winner и epoch increment; новый контекст не активируется старым callback. |

| T13 | UNKNOWN при почти полном окне | Честный transition-eligible checkpoint может сохраниться; resume запрещён до учёта блокирующего исхода. Status возможен при закрытом Gate. |
| T14 | Обязательный payload обрезан/заменён/не доставлен | Delivery не даёт resume. Просто перечисленные правильные ID недостаточны. |
| T15 | Tool call в первом ответе Restore | До guards не исполняется; после них получает самостоятельную актуальную проверку. |
| T16 | Меньший target profile или чрезмерный payload | Нет переключения в непригодную модель; проверена возможность полезного шага либо явно ограниченного recovery. Нет бесконечной compaction. |
| T17 | Attempts/deadline/token budget исчерпан; затем restart | Автоматический лимит не обнуляется; run блокируется без запрещённого вызова. Поздние факты всё ещё сохраняются. |
| T18 | STOP/CANCEL либо изменение цели во время перехода | Новая обычная работа не выдаётся; после STOP служебные LLM-вызовы также не стартуют. Late outcome сохраняется; stale Restore не возобновляет run. |
| T19 | Инъекция, секрет, недопустимая ссылка/получатель | Не происходит повышения доверия или запрещённой передачи. Scan=false не принимается как PASS. |
| T20 | Новая задача, завершение, архивирование/retention | Нет bootstrap обхода; завершённые данные не переполняют payload; активные зависимости не удалены. |
| X01 | Валидный по форме Handoff с неверным следующим шагом | Содержательная проверка известного эталона выявляет ошибку; не выдаётся утверждение о понимании только по schema. |
| X02 | Одинаковый запрос с cache hit и cache miss | Context Budget одинаков при одинаковом input; отличается только экономический учёт. |
| X03 | Независимая инвентаризация обнаруживает скрытый путь compaction | STRICT не подтверждается до перехвата/устранения обхода; неожиданный переход закрывает normal Gate. |
| X04 | Сбой выбранного backend в критических транзакциях | Нет частично consumed допуска, двойного winner или битой ссылки. Для power-loss заявления проверяется соответствующая среда. |
| X05 | Revoked permit, старый BudgetDecision, ресурс изменился | Все такие NORMAL-dispatch отклонены; повторное потребление decision невозможно. |
| X06 | Две задачи в одной history | В checkpoint присутствуют все незавершённые обязательства раздельно; ссылки и решения не смешаны. |
| X07 | Supersession/отзыв решения/изменение authority scope | Активное представление и обязательный payload обновлены; старое решение не побеждает текущие полномочия. |
| X08 | Reconciliation, cancel, безопасный/небезопасный retry | Все outcome enum сохраняются; CANCELLED_CONFIRMED требует evidence. UNKNOWN/partial effect не дают слепого replay. |
| X09 | Неверные bindings Delivery/epoch/profile/payload | Resume отклонён; исторически правильная Delivery не считается текущей после изменения обязательных данных. |
| X10 | Подключение протокола к уже существующей сессии | До inventory/восстановления нет NORMAL-dispatch; нельзя маркировать пустой bootstrap завершённым. |
| X11 | Модель пытается изменить защищённое состояние/валидатор | Саморазрешение невозможно в заявленной модели угроз; непривилегированный Handoff endpoint не пишет policy. |
| X12 | Аудит допуска и проверка времени его действия | Проверяется состояние на момент consume. Поздняя смена policy не делает прошлое законное действие «незаконным задним числом». |

### 17.3. Обязательные регрессионные проверки контрактов

Помимо каталога, пакет реализации должен машинно проверять следующие свойства:

1. FSM применяет next stage из одного источника; action не возвращает противоречащую стадию. Таймер снимает retry-wait, а не устанавливает его снова.
2. Все enum outcomes проходят сериализатор, schema и реальное сохранение. В частности, CANCELLED_CONFIRMED и FAILED_WITH_EFFECT не теряются на SQL CHECK.
3. BudgetDecision нельзя использовать второй раз или привязать к новым revisions только через новый permit. При отказе транзакция не оставляет частичных изменений.
4. Успех transition принимается из допустимого BLOCKED, но не открывает Gate после STOP. Немодельный status не зависит от ACTIVE и наличия model budget.
5. Freshness использует ContentVersion, а текущая транзакция — state_revision. Смена собственного этапа не запускает бесконечную пересборку checkpoint.
6. Сравнение JSON рекурсивное и различает boolean/number, absent/null и типы контейнеров. Числовая нормализация должна соответствовать явно выбранному JSON-договору.
7. Проверка `no_secret_values` требует значения **true**, а не простого наличия поля. Отдельно проверяется реальное происхождение этой оценки.
8. Admission audit связывается с версиями на момент consume, а не с текущей policy при последующем чтении. Действующие permits проверяются по текущей policy.
9. Все поля native triggers, бюджетов и привязок выражаются в canonical contracts; неизвестные обязательные поля не игнорируются.
10. Validator проверяет реальные state-before/state-after и результаты вызовов. Список имён эффектов или готовый `guards_satisfied=true` не является тестом их исполнения.

Отрицательный тест должен завершаться после проверяемого отказа, не добавляя незаметно новое разрешение оператора. Позитивный и негативный варианты различают ID варианта, а не смешивают несовместимые terminal states в одной fixture.

### 17.4. Уровни доказательности

| Результат | Что подтверждает | Чего не подтверждает |
|---|---|---|
| Ревью документа | Наличие согласованных правил и проверенных контрпримеров | Отсутствие всех возможных ошибок. |
| Проверки contracts/модели | Определённые инварианты и исполняемые сценарии абстрактной реализации | Перехваты и поведение реального host/API. |
| Adapter/SUT conformance | Выполнение каталога конкретной версией runtime и адаптера | Любую будущую версию/другую конфигурацию. |
| Эксплуатационный rollout | Устойчивость в указанной среде и нагрузке | Универсальные power-loss, security или semantic guarantees. |

Тестовый runner не должен возвращать IMPLEMENTATION_READY только из хешей файлов, заполненности матриц и самодеклараций. Статус сопровождается областью проверки, версией SUT, покрытыми/пропущенными сценариями и первичными evidence.

## 18. Порядок реализации и граница достаточности

```text
M0  Инвентаризация в read-only
    Контекстные лимиты, все входы compaction, реальные Gate boundaries,
    существующие Task State / Decisions / operation journal / store.
     │
     ▼
M1  Канонические данные и наблюдение
    Разделить controller/content/context revisions, вести измерения,
    outcomes и checkpoints; сверить прогнозы без запретов.
     │
     ▼
M2  Один сквозной управляемый путь
    PREPARING → publish → transition → accept → Restore → resume.
    Вместе с ним реализовать boot fence, одноразовый допуск и STOP.
     │
     ▼
M3  Отказы и отрицательные сценарии
    Unknown, partial effect, retries, stale payload, late callback,
    store/crash faults; весь каталог применимого профиля.
     │
     ▼
M4  Ограниченный rollout и калибровка
    Сначала наблюдение, затем контролируемое включение STRICT;
    стоимость, полезность Handoff и реальные модели/задачи.
```

Crash recovery входит в первый реально блокирующий путь, а не откладывается на необязательную «боевую доработку». Нет обязательных для всех проектов сроков 24/72 часа, недели ожидания или фиксированного числа сотен переходов. Достаточность выборки и нагрузка задаются риском внедрения и заявленными гарантиями.

### Что фиксирует последующая спецификация привязки

Архитектурные правила выше не переопределяются. Привязка выбирает и обосновывает: точные версии runtime и адаптера; перечень intercepts и формат окончательного запроса; фактические ModelProfile и источники лимитов; service/recovery budgets; физическое хранилище и durability; scope snapshot и ресурсные preconditions; сериализацию и миграции; разрешённые инструменты; таймауты и правила safe retry; тестовые среды, rollout/rollback и retention.

Это параметры реальной среды, а не неразрешённые противоречия протокола. Для них задаются конкретные проверяемые значения до STRICT. Наличие уже работающего механизма в host — основание переиспользовать его, а не реализовать второй рядом.

**Минимально достаточный выпуск:** один последовательный run, четыре логические обязанности, один store, канонический checkpoint, ограниченный Handoff/repair, пять стадий, одноразовая отправка, учёт UNKNOWN, проверенная доставка и исполняемые отрицательные тесты. Всё остальное добавляется только по подтверждённой потребности.
